# [TIL] 대용량 미디어 및 다중 리소스 서빙을 위한 분산 아키텍처 설계 (S3 + CloudFront)

**Topic:** 백엔드 리소스 병목 해결, CDN 보안, 역할 기반 데이터 플로우 최적화

## 📝 1. 배경 및 목표 (Background)
청각 장애인을 위한 자막 및 진동(Haptic) 피드백 제공 서비스를 개발 중이다. 
사용자가 영상을 업로드하면 AI 서버(FastAPI)가 이를 분석해 자막(.vtt)과 진동 데이터(.json)를 생성한다. 프론트엔드(React)에서는 이 3가지 파일(영상, 자막, 진동)을 동시에 지연 없이 재생해야 한다.

초기 설계의 **트래픽 부하, 보안 취약점, 서빙 성능** 문제를 인지하고, 서버 간 역할을 명확히 분리한 고성능 인프라 구조를 설계했다.

---

## 🤔 2. 핵심 설계 포인트 (Key Design Points)

### 1) 백엔드(Spring Boot)의 '데이터 패싱' 제거 (S3 Presigned URL)
* **문제:** 수백 MB의 영상을 Spring Boot가 직접 받아서 S3로 넘기면, 서버 메모리(RAM) 점유율이 치솟고 네트워크 대역폭이 이중으로 낭비된다.
* **해결:** Spring Boot는 **IAM Key**를 활용해 **S3 Presigned URL(일회용 업로드 권한 주소)**만 발급한다. 실제 영상 파일(Binary)은 React에서 S3로 **직접 업로드**하여 백엔드 서버의 부하를 0(Zero)으로 수렴하게 만들었다.

### 2) 프라이빗 콘텐츠 보안 강화 (CloudFront Signed Cookie)
* **문제:** S3 앞에 CloudFront를 두어 성능을 높이더라도, 도메인 주소와 파일명만 알면 누구나 접근 가능한 보안 허점이 존재한다.
* **해결:** 로그인한 사용자만 접근할 수 있도록 **Signed Cookie** 방식을 채택했다. 
    * **Signed URL 대비 장점:** 영상, 자막, JSON 파일이 여러 개일 때 파일마다 개별 서명 주소를 만들 필요 없이, 특정 경로(`/*`)에 대한 '통합 식권(Cookie)' 하나로 모든 리소스를 안전하게 서빙할 수 있어 효율적이다.

### 3) 리소스 서빙 최적화 (CloudFront + HTTP/2)
* **문제:** 영상, 자막, 진동 데이터가 서로 다른 도메인에서 호출되면 CORS 설정이 복잡해지고, 브라우저 연결 지연이 발생한다.
* **해결:** 모든 리소스를 단일 **CloudFront 도메인**으로 통합 서빙한다. HTTP/2 멀티플렉싱을 통해 브라우저가 하나의 커넥션으로 3개 파일을 동시에 스트리밍하게 하여 사용자 경험을 극대화했다.

### 4) 내부 서버(FastAPI)의 통신 효율화
* **문제:** AI 서버(FastAPI)가 외부망(CloudFront)을 통해 데이터를 가져와야 할까?
* **해결:** FastAPI는 외부 사용자가 아닌 내부 시스템이므로 **IAM Access Key**를 사용하여 S3 버킷(원본 저장소)에 직접 접근한다. 캐싱 단계를 생략하고 원본 데이터를 즉시 읽고/쓰도록 설계하여 처리 속도를 높였다.

## 🔄 3. 최종 데이터 플로우 (Data Flow)

### Phase 1: 파일 업로드 및 분석 (Write Path)
1. **[React]** 백엔드에 업로드 허가 요청 (파일명 전달)
2. **[Spring Boot]** IAM 권한으로 **S3 Presigned URL** 생성 및 반환
3. **[React]** S3로 영상 파일 **다이렉트 업로드** (백엔드 부하 제로)
4. **[React]** 업로드 완료 후 백엔드에 상태 업데이트 요청
5. **[Spring Boot]** DB 기록 및 FastAPI에 분석 시작 신호 전송
6. **[FastAPI]** S3에서 영상 직접 다운로드 ➔ 분석 실행 ➔ 자막/진동 파일 S3에 직접 업로드 ➔ 완료 콜백

### Phase 2: 미디어 재생 (Read Path)
1. **[React]** 영상 재생 요청
2. **[Spring Boot]** 권한 확인 후 **CloudFront Signed Cookie** 발급
3. **[React]** 발급된 쿠키를 들고 CloudFront 도메인에 영상/자막/진동 데이터 요청
4. **[CloudFront]** 쿠키 검증 후 캐싱된 데이터를 초고속으로 서빙

## 💡 4. 오늘의 회고
* 단순히 '기능 구현'에 그치지 않고, **확장성(Scalability)**과 **보안(Security)**을 고려한 아키텍처를 고민해 보았다.
* 각 서버(Spring Boot, FastAPI)와 인프라(S3, CloudFront)에 명확한 **책임(Responsibility)**을 부여함으로써, 특정 구간에 트래픽이 몰려도 시스템 전체가 마비되지 않는 구조를 도출해냈다.
* Spring Boot에서 AWS SDK를 연동하여 실제 **Presigned URL 발급 로직**을 구현할 예정이다.

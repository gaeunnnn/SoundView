
# 📝 TIL: 인프라 환경 분리 및 구축 진행 중

## 📅 날짜: 2026-03-09

## 1. 개요

단일 EC2 내에서 개발(Dev)과 운영(Prod) 환경을 완벽히 격리하고, 대용량 영상 처리를 위한 효율적인 백엔드 인프라 아키텍처를 설계 및 구축함.

---

## 2. 주요 설계 원칙

* **물리적 격리:** DB와 Redis를 환경별로 별도 컨테이너로 분리하여 상호 간섭 차단.
* **리소스 최적화:** 메모리 점유가 높은 MinIO는 1개만 사용하되, 버킷(Bucket)으로 환경 구분.
* **네트워크 보안:** 외부 노출이 불필요한 인프라 포트(9000, 3306 등)는 AWS 보안 그룹에서 닫고, 오직 Nginx(443)를 통해서만 안전하게 통신.
* **로컬 개발 편의성:** 팀원 각자 로컬 도커를 사용하여 실제 서버 데이터에 영향 없이 독립적으로 개발 가능하도록 설계.

---

## 3. 상세 아키텍처 구성

### 📂 디렉토리 및 컨테이너 구조

관리 편의성을 위해 `/home/ubuntu` 하위에 도커 컴포즈 파일을 환경별로 분리함.

| 분류 | 디렉토리 | 컨테이너 (Port) | 네트워크 |
| --- | --- | --- | --- |
| **공통** | `/common` | `MinIO` (9000/9001) | `dev-net`, `prod-net` |
| **개발** | `/dev` | `MySQL` (13306), `Redis` (16379) | `dev-net` |
| **운영** | `/prod` | `MySQL` (23306), `Redis` (26379) | `prod-net` |

### 🛠 핵심 통신 흐름 (영상 업로드)

1. **Spring Boot ↔ MinIO:** 도커 내부망(`http://minio:9000`)을 통해 직접 고속 통신.
2. **React ↔ MinIO:** 브라우저 보안(Mixed Content) 해결을 위해 **HTTPS가 적용된 Nginx 도메인**을 경유하여 업로드.
* `https://도메인/storage` ➔ Nginx ➔ `http://minio:9000` (내부 토스)



---

## 4. 트러블슈팅 및 의사결정 기록

* **Redis를 1개만 쓸 것인가?**
* *고민:* 메모리 절약 vs 환경 격리.
* *결론:* **2개로 분리.** 1개 사용 시 코드 단에서 Key Prefix나 DB Index를 분기 처리해야 하는 번거로움이 있고, 휴먼 에러(`FLUSHALL`)로 인한 운영 데이터 증발 위험이 크기 때문.


* **MinIO를 2개 띄울 것인가?**
* *결론:* **1개 유지.** 버킷(Bucket) 개념만으로도 코드 수정 없이 완벽한 격리가 가능하며, 스토리지 서버의 중복 실행은 불필요한 메모리 낭비임.

# 📂 [TIL] 객체지향 설계: IS-A(상속)와 HAS-A(합성)의 균형

## 1. IS-A 관계 (상속, Inheritance)

"A는 B이다"라는 논리적인 계층 구조가 명확할 때 사용합니다.

### ✅ 장점 (Pros)

* **코드의 재사용:** 부모 클래스의 기능을 그대로 물려받아 중복 코드를 획기적으로 줄입니다.
* **다형성(Polymorphism) 활용:** 부모 타입의 변수로 여러 자식 객체를 다룰 수 있어 확장에 유리합니다.
* **직관적인 계층 구조:** 도메인 모델 간의 분류가 명확할 때 구조를 한눈에 파악하기 좋습니다.

### ⚠️ 단점 (Cons)

* **강한 결합도:** 부모 클래스의 변경이 모든 자식 클래스에 파급 효과를 미칩니다.
* **불필요한 기능 상속:** 자식 클래스에게 필요 없는 부모의 메서드까지 강제로 물려받게 됩니다.
* **유연성 부족:** 컴파일 시점에 관계가 결정되어 프로그램 실행 중에 관계를 바꿀 수 없습니다.

---

## 2. HAS-A 관계 (합성, Composition)

"A는 B를 가진다"라는 소유 또는 조립의 관점에서 사용합니다.

### ✅ 장점 (Pros)

* **낮은 결합도:** 각 객체가 독립적이므로 한 클래스를 수정해도 다른 클래스에 미치는 영향이 적습니다.
* **런타임 유연성:** 프로그램 실행 중에 부품(객체)을 갈아 끼우거나 동작을 변경할 수 있습니다.
* **단위 테스트 용이:** 각 부품을 가짜 객체(Mock)로 대체하기 쉬워 테스트 효율이 높습니다.

### ⚠️ 단점 (Cons)

* **구현 복잡도:** 기능을 직접 쓰는 게 아니라 부품에게 일을 시키는 **위임(Delegation)** 코드를 일일이 작성해야 합니다.
* **객체 관리 비용:** 시스템이 커질수록 관리해야 할 객체의 수가 많아지고 관계가 복잡해질 수 있습니다.

---

## 3. 한눈에 비교하기

| 구분 | IS-A (상속) | HAS-A (합성) |
| --- | --- | --- |
| **핵심 키워드** | 재사용, 분류, 계층 | 조립, 유연성, 독립 |
| **관계 결정 시점** | 컴파일 타임 (정적) | 런타임 (동적) |
| **캡슐화** | 화이트박스 재사용 (내부 노출) | 블랙박스 재사용 (내부 은닉) |
| **적합한 상황** | "is a" 관계가 영구적이고 명확할 때 | 기능의 조합이나 교체가 빈번할 때 |

---

## 4. 결론: 상황에 따른 선택

* **상속(IS-A)**은 클래스 간의 관계가 매우 긴밀하고, 부모의 기능을 자식이 100% 거부감 없이 수용할 수 있을 때 강력한 도구가 됩니다.
* **합성(HAS-A)**은 변화가 잦은 비즈니스 로직이나, 다양한 기능을 조합하여 새로운 객체를 만들어야 할 때 설계의 유연성을 제공합니다.

> **"상속은 올바르게 사용하면 강력하지만, 불확실한 상황에서는 합성이 더 안전한 선택지가 될 수 있다."**



# [DB] 클러스터 인덱스 vs 비클러스터 인덱스 완벽 정리

## 1. 개요

인덱스는 데이터 레코드를 빠르게 찾기 위한 `<키, 포인터>` 쌍의 자료구조다. 하지만 모든 인덱스가 똑같이 작동하는 것은 아니다.

## 2. 클러스터형 인덱스 (Clustered Index)

> **비유: 영어 사전** (단어 자체가 정렬되어 있고, 찾으면 바로 옆에 뜻이 있음)

* **특징:**
* **물리적 정렬:** 테이블의 실제 데이터 행(Row) 자체가 인덱스 순서에 맞춰 물리적으로 정렬됨.
* **테이블당 1개:** 물리적 순서는 하나뿐이므로 PK(기본키)가 보통 이 역할을 수행함.
* **별도 테이블 없음:** 인덱스 구조(B-Tree)의 리프 노드(Leaf Node)에 **실제 데이터 전체**가 들어있음.


* **장점:** 조회 속도가 가장 빠름 (주소를 들고 다시 찾아갈 필요가 없음).
* **단점:** 데이터 삽입/수정 시 무거운 실제 데이터를 통째로 재배치해야 하므로 **페이지 분할(Page Split)** 부하가 큼.

---

## 3. 비클러스터형 인덱스 (Non-Clustered Index)

> **비유: 책 맨 뒤의 '찾아보기'** (별도의 페이지에서 단어를 찾고, 적혀있는 페이지 번호로 이동함)

* **특징:**
* **논리적 정렬:** 실제 데이터는 무작위로 있고, 인덱스만 따로 정렬됨.
* **별도 공간 존재:** 실제 데이터와 분리된 **별도의 인덱스 테이블**을 생성함.
* **리프 노드의 내용:** `인덱스 컬럼 값` + `실제 데이터가 있는 주소(RID/PK)`가 들어있음.


* **장점:** 테이블당 여러 개 생성 가능. 클러스터형보다 데이터 삽입/수정 시 물리적 이동 부하가 상대적으로 적음.
* **단점:** 인덱스에서 주소를 찾고, 그 주소로 실제 데이터를 한 번 더 찾아가야 하므로 조회 속도가 클러스터형보다 느림.

---

## 4. 팩트 체크: "쓰기 작업이 많은 곳에 써도 될까?" (중요!)

일부 자료에서는 "비클러스터형이 쓰기 속도가 빠르니 업데이트가 잦은 곳에 써라"고 하지만, 이는 **위험한 오해**다.

| 구분 | 비교 관점 | 결론 |
| --- | --- | --- |
| **상대적 비교** | 클러스터 vs 비클러스터 | 비클러스터가 물리적 데이터 이동이 적어 **상대적으로** 빠름. |
| **절대적 관점** | 인덱스 없음 vs 인덱스 있음 | 인덱스가 있으면 쓰기 시 **인덱스 트리도 매번 갱신**해야 하므로 무조건 느려짐. |

> **💡 결론:** 쓰기(INSERT, UPDATE)가 빈번한 컬럼에는 **어떤 인덱스든 최소화**하는 것이 성능 최적화의 정석이다.

---

## 5. 핵심 요약 (Cheat Sheet)

| 비교 항목 | 클러스터형 (Clustered) | 비클러스터형 (Non-Clustered) |
| --- | --- | --- |
| **물리적 정렬** | 데이터 자체가 정렬됨 | 인덱스 페이지만 정렬됨 |
| **리프 노드** | 실제 데이터 행(Row) 전체 | 키 값 + 데이터 위치 포인터 |
| **별도 인덱스 페이지** | 생성 안 함 (테이블 자체가 인덱스) | 생성함 (추가 저장 공간 필요) |
| **조회 속도** | 매우 빠름 | 빠름 (하지만 추가 탐색 발생) |
| **DML 성능** | 느림 (페이지 분할 부담 큼) | 상대적으로 나음 (하지만 오버헤드 존재) |

### 1. MySQL의 실행 계획 캐싱 (Stored Procedure vs Ad-hoc)

* **MySQL의 특징:** Oracle과 달리 전역적인 '공유 실행 계획 캐시' 공간이 없으며, 대신 **커넥션(세션) 단위**로 캐싱을 수행함.
* **저장 프로시저(SP)의 오해:** "SP만 실행 계획을 캐싱해서 빠르다"는 것은 반만 맞는 말. 현대 DB에서는 `PreparedStatement`를 사용하면 일반 쿼리도 실행 계획이 캐싱됨.
* **SP의 진짜 강점:** 네트워크 통신 횟수 감소(Round-trip). 여러 쿼리를 하나의 프로시저로 묶어 호출하므로 앱-DB 사이의 트래픽을 줄임.

### 2. PreparedStatement: 성능과 보안의 핵심

* **개념:** 쿼리의 뼈대(Template)를 미리 DB에 보내 파싱해두고, 실행 시점에는 바인드 변수(`?`)에 데이터만 갈아 끼워 실행하는 방식.
* **장점:**
* **성능:** 매번 하드 파싱을 하지 않고 소프트 파싱(캐시 재사용) 유도.
* **보안:** SQL 인젝션 공격을 원천적으로 차단 (입력값을 단순 데이터로 처리).



### 3. 아키텍처 관점의 저장 프로시저 (SP) 활용 고민

* **EC2 + RDS(Docker) 환경:** 로컬 네트워크 통신은 지연 시간이 매우 짧으므로 SP의 네트워크 절감 효과가 미미함.
* **결론:** 성능 1~2%를 위해 유지보수성(Git 버전 관리 불가, 테스트 어려움)을 포기하는 것은 안티 패턴. 비즈니스 로직은 **애플리케이션 계층(Spring Boot Service)**에서 처리하는 것이 권장됨.

### 4. 데이터의 분류 (정형/반정형/비정형)

* **비정형 데이터:** 이미지, 동영상 등 **고정된 스키마(RDBMS의 행/열)가 없는** 데이터.
* **주의사항:** "구조가 아예 없다"는 표현은 틀림. 파일 자체의 내재된 구조는 있으나, 미리 정의된 데이터 모델을 따르지 않을 뿐임.
* **텍스트의 함정:** 단순 텍스트는 비정형이지만, JSON/XML/HTML처럼 메타데이터를 포함한 텍스트는 **반정형 데이터**로 분류함.
